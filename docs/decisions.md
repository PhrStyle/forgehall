# Decision log

Short decisions that do not need a full ADR, one Y-statement each. Structural, hard-to-reverse decisions live in [docs/adr](adr/0000-record-architecture-decisions.md); see ADR 0000 for how the two relate.

| Date | Area | Decision |
|---|---|---|
| 2026-10-13 | Routing | In the context of choosing a model per run on limited subscription usage, facing no data yet on what works, we chose deterministic rules (v1) over a learned or LLM-based router, to achieve predictable, explainable routing with the reason stored on each run, accepting that the rules are coarse until run data can tune them. |
| 2026-10-13 | Isolation | In the context of isolating agent environments, facing the need to iterate quickly, we chose Docker containers first and Incus VMs later (phase 5) over starting with VMs, to achieve fast feedback with tooling already installed, accepting weaker isolation (shared kernel) until VMs arrive. |
| 2026-10-13 | Stack | In the context of building bus, runner and console, facing a one-maintainer project, we chose a TypeScript monorepo (pnpm, Fastify, the MCP SDK, postgres.js, zod) over a polyglot stack, to achieve shared types and schemas across packages, accepting less raw performance than a systems language. |
| 2026-10-13 | License | In the context of publishing the project, facing the wish to allow broad use and contribution, we chose Apache-2.0 over MIT or a copyleft licence, to achieve permissive use with an explicit patent grant, accepting that derivatives may be closed. |
| 2026-10-13 | Docs | In the context of documenting an open-source project, facing an originally Portuguese design draft, we chose English documentation over Portuguese, to achieve a wider contributor and reader base, accepting translation work. |
| 2026-10-13 | Accounts | In the context of multiple Claude accounts per workspace, facing Anthropic's Usage Policy against using multiple accounts to get around restrictions, we chose single or manual switching between the user's own accounts over any automatic failover, to stay within the terms, accepting that the queue pauses at the limit. (Revised 2026-10-14 after a terms review: failover removed, not just off by default.) |
| 2026-10-13 | Usage | In the context of tracking how much of the plan is used, facing no public usage endpoint, we chose to read usage from the CLI's own `rate_limit_event` (5-hour and 7-day windows) over estimating from token counts, to achieve real numbers that match the account, accepting dependence on an undocumented event format. |
| 2026-10-13 | Approvals | In the context of the `pull_request` policy, facing reviewers that depend on the change, we chose to pick reviewers at approval time over fixing them in config, to achieve the right reviewers per change, accepting one extra step when approving. |
| 2026-10-13 | Git | In the context of commits made by agents, facing different expectations per context (personal versus company), we chose a commit identity configurable per workspace over one global identity, to achieve attribution that fits each context, accepting a little more configuration. |
| 2026-10-13 | Deployment | In the context of where Forgehall runs, facing credentials and data that should not leave the user's control, we chose running on the user's own machine over a hosted service, to achieve local data and no token brokering, accepting that the user operates the stack. |
| 2026-10-13 | Naming | In the context of naming the project, facing that "TeamForge" conflicts with a Digital.ai product, we chose Forgehall over TeamForge, to achieve a name free of that trademark conflict, accepting a rename of anything that used the old working name. |
| 2026-10-13 | Models | In the context of which models the router may pick, facing that Fable is not included in Team Standard seats, we chose Haiku, Sonnet and Opus only over including Fable, to achieve runs that fit the plan's included usage, accepting that Fable cannot be selected until plan support changes. |
| 2026-10-13 | Git | In the context of company repositories, facing read-only provider tokens for agents, we chose a bus-hosted staging remote with publishing by the bus after approval over giving agents push access, to keep every write to the provider behind a human decision, accepting one more component on the bus. |
| 2026-10-13 | Git | In the context of different company policies, facing rules on commit identity and AI attribution, we chose per-workspace `git.author` and `git.ai_trailer` applied by the bus over a global setting, to fit each employer, accepting one more setting to configure. |
| 2026-10-14 | Schedules | In the context of recurring agent work, facing that OS cron and Claude Code `/loop` live outside the bus or inside one session, we chose schedules stored and fired by the bus as normal threads over external schedulers, to keep queueing, routing, usage guards and approvals in one place, accepting that schedules only fire while the bus runs. |
| 2026-10-14 | Reliability | In the context of failed runs, facing an immediate re-queue loop found in testing, we chose backoff (30 s, 60 s) with at most 3 consecutive failures before blocking the thread, and immediate blocking on login errors, over unlimited retries, to protect usage limits, accepting that a human must unblock the thread. |
| 2026-10-14 | Billing | In the context of running agents unattended, facing that an API key in the environment silently switches Claude Code to per-token billing, we chose an opt-in `FORGEHALL_BILLING=subscription-only` runner mode (strip pay-per-use variables, stop runs on a non-subscription credential or paid overage) over a hard-coded rule, to let operators who need it make money charges impossible without limiting everyone else, accepting that the safe mode must be turned on. (Revised 2026-10-15: the mode now follows the credential by default, subscription only with a subscription token, so nobody has to turn it on; `FORGEHALL_BILLING` only forces a mode.) |
| 2026-10-14 | Git | In the context of publishing approved work, facing that a merge needs a checkout and that conflicts need a human, we chose to merge in the bus without a working tree (`git merge-tree --write-tree`, then a merge commit) and to refuse conflicting branches over resolving them or merging in a checkout, to achieve a merge that touches no files on disk and never guesses, accepting that conflicts go back to the agent as a request for changes. |
| 2026-10-14 | Approvals | In the context of approving repository work, facing that an agent can push again after asking, we chose to pin each approval to the branch commit it was requested for and to refuse the merge if the branch moved over merging whatever the branch holds, to ensure you approve exactly what you reviewed, accepting a new approval request after every further push. |
| 2026-10-14 | Runs | In the context of several agents working in one thread, facing that they share one branch, we chose at most one running run per thread over parallel runs with per-agent branches, to avoid races on the branch and its checkout, accepting that messages to a busy thread wait. |
| 2026-10-14 | Runner | In the context of long threads and shared machines, facing the per-argument size limit and process lists that show arguments, we chose to send the prompt through stdin and the MCP config (with the agent token) through a private temporary file over command-line arguments, accepting a temp file per run. |
| 2026-10-14 | Security | In the context of a console API that acts with your authority (approvals, settings, permission answers), facing agents that share a Docker network with the bus, we chose a bearer admin token (`~/.forgehall/admin-token`, mode `0600`) required on everything under `/api`, injected by the console's dev server and used by `fh`, over relying on loopback or network placement, to ensure agents cannot act as you even though they can reach the bus, accepting one more secret to protect. |
| 2026-10-14 | Deployment | In the context of isolating agents in containers, facing that rootless Docker and Docker Desktop containers cannot reach services on the host, we chose to run the bus in the Docker stack (published on `127.0.0.1:4545` only, reachable by agents as `http://bus:4545`) over a bus on the host behind a gateway listener, to achieve the same setup on every Docker flavour, accepting that bus changes need `docker compose ... up -d --build`. |
| 2026-10-14 | Permissions | In the context of tool use that no rule covers, facing a user who may be away, we chose a 15-minute expiry (`PERMISSION_TIMEOUT_MS`) after which the request counts as denied and the agent is told not to retry, over waiting forever or approving by default, to keep runs from hanging and never to act without an answer, accepting that a late answer is lost and the agent must ask again. |
| 2026-10-14 | Permissions | In the context of agents allowed to run directly on the host, facing that a remembered rule would turn one answer into a lasting grant on your own machine, we chose that host mode never uses standing rules (no default allow, no "Always allow" additions) and asks for every tool use that is not denied, over reusing the isolated defaults, to keep the least isolated mode the most supervised, accepting many prompts on the host. |
| 2026-10-14 | Git | In the context of publishing approved work with a per-workspace commit identity, facing agent commits authored as `atlas (forgehall)` and employers that require their own identity and no AI marker, we chose to squash each approval into one commit authored by the workspace identity over merge commits that keep the agents' history, to achieve upstream history that follows each workspace's rules, accepting that the per-run commits stay only in the staging remote. |
| 2026-10-14 | Approvals | In the context of the `pull_request` policy, facing that hosts can notify through webhooks but the bus runs on a laptop without a public address, we chose polling the pull requests the bus opened (`PR_POLL_SECONDS`, default 2 minutes) over webhooks, to work behind NAT with no extra setup, accepting a delay of up to one interval before a thread closes. |
| 2026-10-14 | Approvals | In the context of agents closing their own threads, facing an agent that called `complete` with changes nobody approved, we chose to refuse `complete` while the branch has unmerged commits and to turn a completion made before the push into an approval request, over trusting the prompt, so that changes never close without the user, accepting one more check per completion. |
| 2026-10-15 | Workflow | In the context of having a QA agent check changes before approval, facing workspaces that have no QA agent and repositories whose CI already enforces checks, we chose to express the review step in the developer agent's identity ("ask vigil to verify before request_approval") over a verification enforced by the bus, to keep workflows flexible per workspace, accepting that an agent may skip it and that hard guarantees belong to the repository's CI and branch protection. |
